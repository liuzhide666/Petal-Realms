# V5.21 save integrity and compact crafting

Base: 29b72963275d6532044b7472eb89c8ccac372c22 (V5.20). User scope: repair saves and simplify the crafting interface; clear animation, ordered material selection, nearby actions, single/batch/all without excessive complexity.

## Decisions and alternatives

- Retain the existing version-5 character format and localStorage keys. One previous valid generation is smaller and easier to recover than introducing a database or a migration. Cloud revision/CAS protocols remain in place.
- All means **all of the selected source stack**, not all bag groups. This avoids accidentally spending unrelated rare cards. Automatically feeding new products into higher-rank recipes was rejected because it changes cost and scope during confirmation.
- Retain current per-rank success probabilities, guaranteed rank 7 conversion and uniform failure loss. No new pity counter or economic rebalance is introduced without a separate model and simulation of those rules.
- Show material catalog on the left and selected recipe/actions on the right on desktop and phone. Keep exact five-attempt probability analysis in an expandable section; it does not forecast the entire all operation.

## Persistence contract

`PetalSaveStore` validates the current payload before returning it. A missing primary and previous copy permits a new character. Invalid stored bytes do not. A valid previous copy can recover the character; otherwise verified local login exposes a file recovery action. Replacing invalid bytes first retains one damaged copy. Changed writes rotate one valid previous generation; identical autosaves do not overwrite that recovery point. Storage errors remain errors rather than becoming a fresh character.

`saveGame()` returns the outcome of the local commit. Cloud queue failures cannot convert a successful local commit into failure, and the queued snapshot is detached from mutable gameplay inventory. Export reads the current in-memory payload, so a quota error does not force export of stale disk state. Manual save messages distinguish failure, local persistence and separate cloud status.

Existing guarded confirmations still reject stale account/player/view changes. Live service conflicts and pending outboxes retain their existing explicit choice and conditional-write rules; no automatic inventory merge is added.

## Crafting contract

| Mode | Work bound | Confirmation |
| --- | --- | --- |
| Single | At most 1 attempt | Direct, with rate and loss visible |
| Batch | At most 5 attempts | Shows selected type, quality, stock and loss rules |
| All selected stack | Until source <5 or output reaches 99999 | Explicitly excludes other groups and recursive upgrades |

An attempt requires five source copies; success consumes five and produces one next-rank copy; failure consumes uniformly 1–4. Rank 9 cannot upgrade; rank 7 needs no random roll. Protection and output capacity are checked before RNG/material consumption. Equipped cards are outside bag inventory and cannot be spent.

One guarded operation settles against a copied bag. A failed local commit restores the original bag and presents an error rather than an awarded product. RNG draws already made by the failed attempt can advance the session craft stream; rollback does not reset it. The worst-case all bound is initial stock minus four (stock is capped at 99999), since each attempt consumes at least one card.

After a successful commit, one short aggregate receipt shows attempt count, successes, failures, actual spent material, remaining material and products. The existing 950 ms gather/emerge/scatter presentation remains cancellable; reduced motion is 180 ms. Skip, close and visibility changes cannot perform settlement again. There is no sequential animation per attempt for all mode.

## Acceptance

- Local corruption cannot silently overwrite an existing character with level 1.
- Valid recovery, quota failure, export during failure, cloud queue exceptions and isolated account keys are tested.
- Rapid activation accepts once; stale confirmation, protection, capacity and terminal rarity consume nothing.
- All never crafts its own products; failed-only runs terminate and receipts reconcile inventory.
- Both columns fit 1280×800, 390×844, 320×568, 844×390 and 568×320 without horizontal body overflow.
- Search and quality filtering remain operable. Action targets are at least 44 px high. Exact probability charts are reachable by opening their summary.

Production rollout is a separate recorded action. Candidate source or local browser success alone is not evidence of a deployed website.
